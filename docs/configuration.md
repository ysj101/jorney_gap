# Configuration validation

`@journeygap/core` exports `validateConfig(unknown)` and `validateRelayConfig(unknown)`. Both return `{ valid: true, value }` with a cloned, normalized configuration or `{ valid: false, errors }`. Validation does not mutate its input or include rejected values in errors. Omitted journey timeouts default to 30 minutes and Relay retention defaults to 14 days.

Public types (`JourneyGapConfig`, `JourneyDefinition`, `RelayConfig`) are inferred from the same schema source used to generate the packaged `schema/journeygap.schema.json` and `schema/relay.schema.json`. After modifying that source, run `pnpm build && pnpm schema:generate`. CI runs `pnpm schema:check` and fails if checked-in JSON is stale. JSON Schema can be imported using `@journeygap/core/schema/journeygap.schema.json` and the corresponding Relay path.

Runtime validators are precompiled by AJV and checked into source, so importing and using core does not require `eval` or `new Function`. After changing schemas, also run `pnpm validators:generate && pnpm build`. CI checks generator output with `pnpm validators:check`. Node tests exercise the built package under `--disallow-code-generation-from-strings`; browser CSP behavior is also part of the later E2E acceptance tests.

Use the validation functions for the complete contract: the portable JSON Schemas enforce shape, bounds, scalar types and ID syntax; additional semantic checks enforce unique IDs, an exclusively final terminal step, simple route segments, and safe endpoint/origin URLs. A generic JSON Schema validator alone does not enforce those cross-field constraints.

Both configurations reject unknown properties. Web configuration requires schemaVersion 1, enabled, serviceName, a public otlpTracesEndpoint, opt-in consent with compact or external UI, and at least one journey. Each journey has 2–20 uniquely named steps, with only the last marked terminal, and a timeout of 1–1440 integer minutes. IDs start with a lowercase letter and contain up to 64 lowercase letters, digits, periods, underscores, or hyphens. Route patterns use slash-separated literals or `:parameter` segments, never regular expressions; route IDs and patterns must be unique.

Endpoints must end in `/v1/traces`, use HTTPS (loopback HTTP is permitted for local development), and contain no credentials, query, or fragment. This applies even when disabled: the CLI can supply a safe placeholder when generating disabled configuration. Browser authentication headers are not accepted. Custom attribute allowlists contain at most 10 unique `app.` keys of up to 64 characters; actual attribute values require further runtime privacy filtering.

Relay configuration uses the same journey definition. It requires nonempty explicit allowedOrigins and services, retentionDays (1–365), and rateLimitPerMinute (1–100000). Wildcards, origin paths and credentials are rejected. HTTPS origins and local loopback HTTP origins are supported. Service names are unique; journeys are unique within each service. Optional maxDatabaseBytes and maxEvents configure storage quotas. An ingest caller must also match an explicitly configured journey and step using `isDefinedStep()`.
