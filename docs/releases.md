# Release procedure

There are no published packages or production deployments. Package/scope names are provisional. Implementation completion does not authorize npm publication. Before the first release, a maintainer must separately confirm publication authorization, npm scope/name ownership and availability, name/trademark review, repository access, package licensing/notice obligations, SemVer/changelog and migration notes. None of those rights checks are inferred from a passing build.

CI runs build, schema/static-validator synchronization, typecheck, lint, unit/integration, browser E2E, standard Collector acceptance, dependency audit (high/critical block), license/package-content checks, redacted Git-history secret scanning and workflow lint. Action SHAs and downloaded security-tool versions/SHA256s are fixed. Gitleaks scans all fetched Git history; the only exemption is the exact public consent preference storage key in its consent module. Findings print rule/file/line metadata, never secret values. Heuristic scanning is not a guarantee that every possible credential is absent. No test-directory or fake-token blanket exemption exists.

`pnpm licenses:check && pnpm release:pack` prepares the four real npm archives, dependency inventory, release metadata binding the source commit/version, and SHA256SUMS in artifacts/release. `node scripts/pack.mjs --verify [directory]` verifies content, package identity, version, expected filenames and immutable source revision. Tests reject altered archives and commit mismatches. These commands do not publish.

The Release workflow is manual-only. Dispatch it from main with an existing exact v<SemVer> tag. Validation starts from trusted main workflow code, verifies the tag is on main, verifies matching package version and successful main CI jobs check/containers/security, and verifies that npm-release has a required human reviewer and only main is permitted. It then checks out the validated immutable commit, rechecks/builds/packs and uploads the exact candidate archives for review. No job runs merely because a tag is pushed.

The default publish=false only prepares artifacts. A separately authorized publication request must explicitly set publish=true and names_and_rights_confirmed=true. After candidate artifacts are available, the publish job waits for the npm-release environment's human approval. The repository environment is configured with maintainer ysj101 as required reviewer and main as its only allowed branch. The sole maintainer may approve their own dispatch as a separate final review; repository owners can administratively change protection rules, so review those settings before release. No approval has been requested or granted for publication during implementation.

After approval, a fresh job checks out the candidate SHA, downloads only that run's archives, verifies checksums/source binding again and publishes core → web → relay → cli with public access, provenance and lifecycle scripts disabled. Only that job has id-token:write. No long-lived npm token is configured. Configure npm trusted publishing for ysj101/jorney_gap, workflow release.yml and environment npm-release, explicitly allowing direct npm publish. The workflow uses Node 24 and npm 11.6.2, above npm's documented OIDC minimum. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) and [GitHub environment review](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

Trusted publishing requires package-side npm setup. New names may need a separately authorized bootstrap/reservation step before that setup is possible. The workflow deliberately has no token fallback; missing registry trust fails publication. Do not use an implementation task to bootstrap public packages or grant registry rights. Partial publication can occur if the registry rejects a later package; inspect actual registry versions and use a corrected patch release rather than automatic unpublishing. Real service deployments are a separate operator action.

All packages currently use 0.1.0 prerelease development versions. A breaking public API/schema change requires a major version; keep schemaVersion 1 compatible. SQLite v2 migrates v1 records transactionally and adds source/provenance metadata; back up the DB before upgrading, and do not downgrade a v2 database to a v1 reader. Retain the installation manifest when upgrading CLI-managed integrations so uninstall can protect user edits. Record future migrations in CHANGELOG before a tagged release.
